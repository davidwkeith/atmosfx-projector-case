# Updates and backup

## Updates

VideoFX never updates itself without being asked, and the web page never touches the network. A timer (`videofx-update-check.timer`, daily) runs `videofx-update --check` as root; the System page then shows **Upgrade to X.Y.Z**, and **Check now** asks right away. **Upgrade** is authorized the way Home Assistant does it: the web layer authenticates and a privileged helper does the work. The page password is the authorization: with none set, the page shows the update but offers no button (anyone on your network could press it), so set one or run `sudo videofx-update`. The page never asks for the Pi's login password, which would cross the network in plain HTTP. The unprivileged, sandboxed service cannot install anything itself, so it sends the request over `/run/videofx-upgrade.sock` to a small root helper (`src/upgrade-helper.js`, started per connection by `videofx-upgrade.socket`). The socket is mode 0600 and owned by the service account, so no other local user can reach it. The helper starts `videofx-update` as a transient unit and never sees a password. `update-check.json` is only ever replaced by rename, never through a link. The page password itself travels over plain HTTP, so use the page only on a LAN you trust. With the read-only root, updates go through maintenance mode, which `videofx-update` handles:

```sh
sudo videofx-update --check                   # asks GitHub; the page then shows "update available"
sudo videofx-update                           # latest release
sudo videofx-update --tag v0.3.0 --os         # a given release, plus apt full-upgrade
sudo videofx-update --tarball ~/videofx-pi-0.3.0.tar.gz   # no GitHub API needed: scp the tarball and its .sigstore.json over first
sudo videofx-update --rollback                # back to the previous version
```

- **What it does:**
  1. A plain update (no `--tag`, `--tarball` or `--os`) first asks GitHub for the latest release and stops with "Already up to date" if it isn't newer, before anything reboots. If the root is protected, it then records the job and any tarball on the data partition, switches maintenance mode on and reboots. `videofx-update-resume.service` picks the job up after the reboot.
  2. Downloads the release asset `videofx-pi-X.Y.Z.tar.gz` and its `.sigstore.json`, checks the attestation (see below) before unpacking anything, and checks it's VideoFX.
  3. Copies the running version to `/opt/videofx.prev` (with its `node_modules`, so a rollback works offline).
  4. Runs the new release's `system/setup.sh`, which does `apt-get install`, `npm ci --omit=dev`, units and config. Both need the internet, with `--tarball` too.
  5. With `--os`, runs `apt full-upgrade`.
  6. Switches maintenance off and reboots.
  7. If step 4 fails (no network, say), it puts the previous version back, switches protection back on, reboots and exits with an error. It doesn't retry.
- **The log:** the journal is in RAM and an update reboots, so every run also writes to the data partition. `/srv/videofx/update/last.log` is the whole run, including the part after the maintenance reboot (`last.log.1` is the run before; both root-only). Each step also writes `update-last.json` (state, reason, installed version, the last 20 log lines) to `/var/lib/videofx`, which the System page shows under the version and the SSH banner sums up. A run still marked "in progress" an hour later never finished (a power cut, say). Older versions do not write these files, and an update runs the installed version's script, so the first update into this version is not logged.
- **Signed releases:** the new release's `setup.sh` runs as root, so `videofx-update` installs only a tarball that GitHub Actions built and signed. CI attaches a build provenance attestation to each release (`videofx-pi-X.Y.Z.tar.gz.sigstore.json`, a Sigstore bundle from `actions/attest-build-provenance`). The installed version's `videofx-verify-release` (`src/verify-release.js`, with the `sigstore` npm package), never the copy inside the new tarball, checks four things. The bundle's signature chains to Sigstore's public-good certificate authority and is logged in its transparency log (the trust root comes from Sigstore's TUF repository, cached in `/srv/videofx/update/sigstore-tuf`). The signer is this repo's `.github/workflows/build.yml` running on a `vX.Y.Z` tag, not a branch or a pull request. The attestation names the tarball's sha256. The tag matches the version inside the tarball. A release with no attestation is not offered (the check reports "no GitHub attestation"), and a bad one stops the update with nothing installed. An attestation covers bytes, so the version inside must also match the release's, and a plain update (the page's **Upgrade**, or no `--tag`) only moves forward: an old, genuinely attested tarball attached to a new release is refused. Name an older version with `--tag` or `--tarball` to go back on purpose. If a resumed update stops early for any of these reasons, protection is switched back on and the Pi reboots, rather than staying in maintenance mode. `--tarball` needs `FILE.sigstore.json` next to it, or `--bundle`; `--no-verify` installs your own unattested build and works only with `--tarball`. Checking needs the internet (Sigstore's trust root), with `--tarball` too. To check a release file yourself: `gh attestation verify FILE -R davidwkeith/atmosfx-projector-case`.
- **Who can ship an update:** anyone who can push a `v*` tag to the repo, since CI then builds and signs whatever that tag points at. Your tags and commits are SSH-signed and show as Verified on GitHub. A tag ruleset that lets only you create `v*` tags keeps it that way.
- **From the SSH-signed releases:** 0.9.0 and 0.9.1 checked an SSH signature made on the owner's machine (`ssh-keygen -Y`, `allowed_signers`). A Pi on one of those cannot check a GitHub attestation, so move it once by hand: download `videofx-pi-X.Y.Z.tar.gz` and its `.sigstore.json` from the release, check the tarball with `gh attestation verify` on your own machine, then `scp` it over and run `sudo videofx-update --tarball videofx-pi-X.Y.Z.tar.gz --no-verify`. From then on the Pi checks every update itself.
- **Private fork:** if your copy of the repo is private, put a GitHub token with read access to its contents (a fine-grained token, "Contents: read") in `/srv/videofx/update/github-token`, mode 600, owned by root. It lives on the data partition so it survives the read-only root. Or use `--tarball`.
- **Making a release:** bump the version in `pi/package.json`, tag `vX.Y.Z` (signed) and push the tag. CI (`.github/workflows/build.yml`) builds the STLs, `videofx-pi-X.Y.Z.tar.gz` (`pi/tools/make-release.sh`), the public image with its `.sha256`, and `videofx-imager.json` (`pi/tools/imager-json.sh`). It attests them all and publishes the release with the tarball's `.sigstore.json`. The image job runs on GitHub's arm64 runner and takes about ten minutes. The repo has immutable releases: `gh release create` uploads everything to a draft and only then publishes, so a release never appears half-made, and nothing can be swapped afterwards. There is no manual step; a tarball you release by hand has no attestation, and Pis refuse it. The page footer shows the version and sha, and "update available" when the last `--check` found a newer release.

## Backup and restore

System > **Backup** > **Download backup**. That's one JSON file with the settings, schedule, quiet hours, playlist, and the Matter storage (fabrics, keys). Videos aren't included; copy those yourself. The file holds the pairing keys and the password hash, so keep it private. When a password is set, downloading needs it.

**Restore:** pick the file, choose whether to include the Matter pairing, confirm. Settings and playlist apply straight away and the service restarts. A restored pairing is swapped in at that restart, and the previous one is kept as `matter.before-restore`.

- Restore the **pairing** only onto the same Pi, or onto a replacement when the old one is gone for good. Two devices with one Matter identity confuse Apple Home and both misbehave.
- To clone settings onto a second VideoFX, restore **without** the pairing and pair the new one separately.
